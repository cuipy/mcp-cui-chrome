# 版本号管理

## 版本号的来源

版本号按 **git 提交次数**算，不手工拍脑袋定。

算法：

```
提交数 = git rev-list --count HEAD
版本号 = 0.1.<提交数>
```

例如当前提交总数是 13，对应版本号就是 `0.1.13`。

查提交数的命令（在仓库根目录执行）：

```bash
git rev-list --count HEAD
```

> 历史遗留：当前 `package.json` 写的是 `0.1.11`，但提交数已经是 13，说明早期没有严格按提交数走。从现在起按本规范执行。

## 版本号存在哪些文件

版本号散落在下面几处，**每次提交前要同步改**，不要漏。

| 文件 | 位置 | 是否要手动改 | 说明 |
| --- | --- | --- | --- |
| `package.json` | 顶层 `"version"` | 要 | 权威版本，其它地方都跟它对齐 |
| `package-lock.json` | 顶层 `"version"` 和 `packages[""].version` | 一般不用 | 跑 `npm install` 或 `npm version` 会自动同步，别手改 |
| `server.json` | `"version"` 和 `packages[0].version` | 发布时要 | MCP 市场的发布清单，本地开发不受它影响；只在对外发版时改 |

**不用改的地方**：

- 黄条标签（`src/stealth.ts` 的 `barLabel()`）：运行时从 `package.json` 读最后一段，显示成 `cui-chrome[v<最后一段>]`，自动跟着变。
- MCP 服务对外声明的版本（`src/index.ts`）：同样运行时读 `package.json`，不用写死。

## 各文件的用途

- **`package.json`**：npm 包的定义，权威版本源。
- **`package-lock.json`**：锁依赖的精确版本，编译（`npm run build`）不会改它，只有 `npm install` / `npm version` 才会动。
- **`server.json`**：发布到 MCP 应用市场的清单，声明包名、版本、仓库、传输方式（`stdio`）。本地 IDE 连的是 `.codebuddy/mcp.json` 里的 `node dist/index.js`，不读这个文件；只有对外发布时才需要把它和 `package.json` 对齐。

## 改版本的操作顺序

1. 在仓库根目录执行 `git rev-list --count HEAD`，拿到提交数 N。
2. 把 `package.json` 的 `version` 改成 `0.1.N`。
3. 跑 `npm install`，让 `package-lock.json` 自动同步（不要手改锁文件）。
4. 如果是要对外发布，再把 `server.json` 的两处版本也改成 `0.1.N`。
5. 跑 `npm run build` 重新编译 `dist`（编译不改版本号，只是让产物带上新代码）。
6. 重载 MCP 服务，新代码和新版本才会生效。

> 注意：提交本身会让提交数 +1，所以下次算出来的版本号会再大一号。这是预期行为。
